# GSlide Vietnamese Localization Specification

- Status: Implemented; manual Standard/Smart release smoke test remains
- Date: 2026-09-04
- Scope owner: GSlide Web and user-facing API responses

## 1. Objective

Make Vietnamese the default user-interface language of GSlide without changing
the meaning of stored presentation data, template schemas, API identifiers, or
the language selected for generated slide content.

The implementation must also establish a maintainable localization boundary so
that user-facing copy is no longer scattered as hard-coded strings throughout
the application.

## 2. Current state

The initial repository audit found:

- No existing UI localization framework or translation catalog.
- English user-facing strings spread across approximately 118 TypeScript/TSX
  files in `gslide-web/app` and `gslide-web/components`.
- Root document metadata uses `lang="en"` and Open Graph locale `en_US`.
- FastAPI sends English progress messages and error details that are rendered by
  the web application.
- Some English progress text is also used as application state, for example the
  comparison with `"Outline ready"` in `OutlinePage.tsx`. Translating these
  strings directly would risk changing behavior.
- The presentation-content language selector is currently independent from the
  interface language and already supports Vietnamese.

## 3. Product decisions

### 3.1 Default locale

- The default UI locale is `vi-VN`.
- English remains a complete fallback catalog during the migration.
- Locale is not added to route paths. Existing URLs and links must continue to
  work without `/vi` or `/en` prefixes because GSlide is embedded as a miniweb.
- A visible language switcher is not required for the first release. The locale
  layer must allow one to be added later without restructuring components.

### 3.2 UI language versus slide-content language

These are separate concepts:

| Concept | Purpose | Default |
| --- | --- | --- |
| UI locale | Labels, buttons, errors, progress and help text | `vi-VN` |
| Presentation language | Language generated by the LLM inside slides | Vietnamese for new sessions |

Changing the UI locale must never silently rewrite an existing presentation or
change the language of its generated content. The presentation language remains
an explicit generation setting.

### 3.3 Terminology

Use the following terms consistently:

| English source | Vietnamese UI |
| --- | --- |
| Presentation | Bài thuyết trình |
| Slide | Slide |
| Outline | Dàn ý |
| Layout | Bố cục |
| Template | Mẫu |
| Theme | Chủ đề |
| Speaker notes | Ghi chú thuyết trình |
| Generate | Tạo |
| Regenerate | Tạo lại |
| Export | Xuất |
| Dashboard | Trang chủ |
| Community | Cộng đồng |
| Settings | Cài đặt |

Brand names, model names, provider names, file formats, keyboard key names, and
technical identifiers remain unchanged where translating would reduce clarity.

## 4. Functional requirements

### FR-1: Central translation catalogs

- User-facing web copy must be stored in centralized `vi` and `en` catalogs.
- Translation keys must be semantic, grouped by feature, and independent of the
  original English sentence, for example `outline.actions.continue`.
- The Vietnamese and English catalogs must have the same key structure.
- Missing Vietnamese keys must fall back to English in development and must be
  reported as a test/CI failure.
- Messages must support named interpolation parameters and count-dependent text.

Suggested structure:

```text
gslide-web/i18n/
  config.ts
  types.ts
  provider.tsx
  translate.ts
  locales/
    vi.ts
    en.ts
```

The implementation may use a small app-local provider and native `Intl` APIs.
It must not require locale-prefixed routes.

### FR-2: Locale initialization

- The app must render Vietnamese on the first load without a client-side flash
  of English content.
- The root document must use `lang="vi"`.
- Page metadata, Open Graph metadata, loading screens, global error pages, and
  not-found pages must use Vietnamese copy and `vi_VN` metadata.
- If locale persistence is added, invalid stored values must fall back to
  `vi-VN`.

### FR-3: Golden-path localization

All visible copy in the main flow must be localized:

1. Dashboard and empty states.
2. Prompt entry and document upload.
3. Generation configuration.
4. Document preview.
5. Outline generation, review, editing, and regeneration.
6. Template selection.
7. Slide generation progress and recoverable errors.
8. Presentation editor and chat.
9. PDF/PPTX export.

This includes headings, labels, placeholders, buttons, tooltips, dialogs,
notifications, validation messages, loading copy, and accessibility labels.

### FR-4: Secondary-feature localization

The following areas must meet the same localization standard:

- Settings and provider configuration.
- Themes and fonts.
- Community presentations.
- Template management and Template Studio.
- Slide editor toolbars for text, images, icons, tables, charts, selection, and
  layout controls.
- Keyboard-shortcut help.

### FR-5: Stable progress and error semantics

User-facing behavior must not depend on translated prose.

- Frontend state transitions must use machine-readable event types or codes,
  never display messages such as `"Outline ready"`.
- New SSE progress payloads should add a stable code and optional parameters:

```json
{
  "status_code": "presentation.generating_slide",
  "status_params": { "current": 3, "total": 10 },
  "status": "Generating slide 3 of 10"
}
```

- New API error payloads should add `error_code` and optional `error_params`.
- Existing `status` and `detail` fields remain during a compatibility period so
  older clients are not broken.
- The web app translates known codes and uses sanitized `status`/`detail` only
  as a fallback.
- Raw technical errors remain available in logs but must not be the primary UI
  message.

### FR-6: Presentation-language selector

- API values and stored enum values must remain stable.
- Display labels must be localized separately from values sent to the API.
- A new session should default the content language to Vietnamese.
- Existing saved selections must be preserved.
- Auto-detection remains available and must not be relabeled as if it always
  produced Vietnamese.

### FR-7: Formatting

- Dates and numbers shown by the UI must use `Intl.DateTimeFormat` and
  `Intl.NumberFormat` with the active locale.
- File sizes, slide counts, timestamps, and count messages must not be assembled
  with English-only string concatenation.
- User content and LLM-generated content must not be reformatted merely because
  the UI locale is Vietnamese.

### FR-8: Accessibility

- Visible labels and matching `aria-label`, `title`, alt text, and screen-reader
  announcements must be localized together.
- Keyboard keys such as `Ctrl`, `Shift`, `Delete`, and `Backspace` may remain in
  their platform-recognizable form.
- Translation must not remove accessible names from icon-only controls.

## 5. Non-functional requirements

### NFR-1: No regression to generation contracts

Localization must not modify:

- Template IDs or layout IDs.
- JSON schema property names.
- Database column values used as enums.
- Provider/model identifiers.
- SSE event names or API route paths.
- Internal LLM system prompts solely for the purpose of translating the UI.

User instructions passed to the LLM remain verbatim. Only UI chrome and the
explicitly selected presentation language control generated content language.

### NFR-2: Rendering quality

- All product fonts must display Vietnamese diacritics correctly.
- Buttons, tabs, menus, dialogs, toolbars, and mobile layouts must tolerate
  longer Vietnamese labels without clipping or overlap.
- Exported slide content is out of scope for UI-copy translation, but exported
  viewer controls and error messages are in scope.

### NFR-3: Maintainability

- New components must not introduce hard-coded user-facing copy outside the
  translation catalogs, except for documented technical/brand exceptions.
- Translation functions must be usable in client components, server components,
  metadata functions, hooks, and non-React utility code.
- Logging and analytics event names remain stable and English-coded.

## 6. Out of scope

- Translating user-authored presentation content.
- Translating existing generated slides in the database.
- Translating template IDs, component schema keys, CSS properties, or database
  schema names.
- Translating third-party provider responses that cannot be mapped safely.
- Adding locale-prefixed routes.
- Full professional localization into languages other than Vietnamese and
  English.

## 7. Acceptance criteria

The work is complete when:

1. A clean session opens GSlide in Vietnamese with `html[lang="vi"]`.
2. The complete prompt-to-export golden path contains no unintended English UI
   strings.
3. Standard and Smart generation modes both show Vietnamese progress and errors.
4. UI localization does not change the selected presentation-content language.
5. A new session defaults presentation content to Vietnamese; an existing saved
   language remains unchanged.
6. No frontend state transition compares localized display text.
7. All icon-only actions retain meaningful Vietnamese accessible names.
8. Vietnamese diacritics render correctly in every configured product font or a
   documented fallback font is used.
9. `vi`/`en` catalog parity and missing-key tests pass in CI.
10. Existing generation, editing, saving, and export tests continue to pass.

## 8. Release compatibility

Backend event/error code changes are additive for at least one release. The web
client must accept both coded and legacy payloads during that period. Removal of
legacy English `status` or `detail` fields requires a separate compatibility
review.

## 9. Localization implementation conventions

These conventions are binding for future localization work:

- Catalogs live in `i18n/locales/vi.ts` and `i18n/locales/en.ts`; their key
  trees must remain identical. `tests/i18n-catalogs.test.mjs` enforces parity.
- Client components use `useT()` from `@/i18n/provider`. Server components,
  metadata, hooks outside React, and utilities use `translate()` from
  `@/i18n/translate`.
- Keys describe product meaning rather than copying an English sentence, for
  example `settings.text.selectProvider`.
- Interpolation uses named parameters. Count-dependent messages use function
  leaves instead of assembling English fragments in components.
- Translate visible product copy, accessibility copy, validation messages,
  toasts, and product-owned placeholders.
- Do not translate brands, provider/model names, file formats, technical
  identifiers, enum/API values, URLs, logs, user content, imported content, or
  LLM-generated content.
- Never translate a string in place when it participates in a comparison,
  switch, or state transition. Introduce a stable internal code and translate
  only its display label.
- New keys must be added to both catalogs in the same change. Run TypeScript,
  catalog parity, scoped ESLint, and the localization test suite before merge.

### 9.1 Translation namespace map

| Namespace | Product area |
| --- | --- |
| `common`, `nav`, `metadata`, `loading`, `errors`, `config` | Shared application chrome and startup states |
| `dashboard` | Presentation list, cards, empty states and actions |
| `upload`, `documentsPreview`, `outline` | Prompt, documents, configuration and outline review |
| `presentation`, `presentation.chat`, `export` | Generation, editor, chat and export |
| `settings`, `themes`, `community`, `templates` | Dashboard secondary features |
| `templateStudio`, `templateEditor`, `slideEditor` | Template and slide authoring tools |

### 9.2 Intentional English and technical exceptions

- `GSlide`, OpenAI, Google, Gemini, SearXNG and model names.
- PDF/PPTX and keyboard-key names such as Ctrl, Shift, Enter and Escape.
- Provider IDs, layout tokens, API fields, route paths, schema keys and
  state-machine constants.
- Font specimen copy and user-style sample/template data that is not product
  chrome.
- Dynamic tool/model diagnostic prose. The surrounding activity label is
  localized from a stable code; diagnostic content remains verbatim.

## 10. Stable backend message contract

This section is the authoritative contract shared by `gslide-api` and
`gslide-web`. Display prose is retained for compatibility, while application
behavior and localization use codes.

### 10.1 Wire formats

SSE status event:

```json
{
  "type": "status",
  "status": "Searching with SearXNG: example query",
  "status_code": "outline.searching_provider",
  "status_params": { "provider": "SearXNG", "query": "example query" }
}
```

SSE error event adds optional `error_code` and `error_params` beside the
existing `detail`. Chat trace dictionaries add optional `code` and `params`
beside `kind`, `status`, and `message`. HTTP errors raised through
`CodedHTTPException` use:

```json
{
  "detail": "Number of slides cannot be greater than 20",
  "error_code": "error.slides_too_many",
  "error_params": { "max": 20 }
}
```

The optional code/param fields must be omitted when unset. Existing `status`,
`detail`, and `trace.message` fields retain their wording during the
compatibility window. Params are flat JSON objects with stable snake_case
names and string/number values. `safe_sse_stream` forwards codes from
`CodedHTTPException`; plain exceptions preserve the legacy shape.

### 10.2 Status registry

| Flow | Codes |
| --- | --- |
| Outline | `outline.preparing`, `outline.analyzing_topic`, `outline.searching_provider`, `outline.web_research_complete`, `outline.native_search_drafting`, `outline.drafting` |
| Smart generation | `smart.preparing`, `smart.reading_documents`, `smart.searching_web`, `smart.applying_community`, `smart.designing_complete` |
| Chat status | `chat.reading_deck_context`, `chat.finalizing_response`, `chat.saving_chat` |

`outline.searching_provider` carries `provider` and `query`. Other status
codes currently require no params.

### 10.3 Chat trace registry

The implemented trace codes are:

- Outline/deck actions: `chat.trace.adding_outline_slide`,
  `chat.trace.updating_outline_slide`, `chat.trace.deleting_outline_slide`,
  `chat.trace.adding_blank_slide`, `chat.trace.adding_slide_from_layout`,
  `chat.trace.updating_slide`, `chat.trace.deleting_slide`.
- Reading/searching: `chat.trace.reading_template_summary`,
  `chat.trace.reading_smart_deck_context`,
  `chat.trace.reading_source_documents`,
  `chat.trace.searching_relevant_slides`,
  `chat.trace.opening_requested_slide`,
  `chat.trace.checking_available_layouts`,
  `chat.trace.checking_layout_schema`,
  `chat.trace.checking_available_themes`.
- Slide/component work: `chat.trace.generating_slide_assets`,
  `chat.trace.saving_slide`, `chat.trace.adding_slide_element`,
  `chat.trace.updating_slide_element`, `chat.trace.removing_slide_element`,
  `chat.trace.adding_slide_component`,
  `chat.trace.creating_slide_component`,
  `chat.trace.updating_slide_component`,
  `chat.trace.removing_slide_component`,
  `chat.trace.applying_presentation_theme`.
- Tool lifecycle: `chat.trace.running_tool`, `chat.trace.using_tools`,
  `chat.trace.tool_failed`, `chat.trace.tool_result`,
  `chat.trace.tool_returned_results`, `chat.trace.found_requested_data`,
  `chat.trace.no_matching_data`, `chat.trace.tool_completed`,
  `chat.trace.tool_limit_reached`, `chat.trace.model_note`.

`running_tool` carries `tool`; `using_tools` carries a comma-joined `tools`
value; tool result/lifecycle events may carry `tool`, `count`, `reason`, or
`recovery`. `model_note` and `tool_result` intentionally retain dynamic prose
while their stable activity labels are localized.

### 10.4 Error registry

SSE catch-all codes:

- `error.outline_parse_failed`, `error.outline_slide_count`,
  `error.outline_generation_failed`.
- `error.slides_generation_failed`, `error.smart_generation_failed`,
  `error.chat_stream_failed`.

HTTP error families:

| Family | Covered conditions |
| --- | --- |
| `error.*` generation | Invalid/missing templates and layouts, prompt/outline/slide-count validation, missing presentations/slides, structure mismatch and generation task failures |
| `error.image.*` | Type, empty/invalid uploads, retrieval/upload/delete and generation failures |
| `error.file.*` | Missing documents/files, size limits and rejected types |
| `error.template.*` | Read-only/missing templates, PPTX/layout/image validation and template mutation failures |
| `error.theme.*`, `error.slide.*` | Missing themes/logos/slides and invalid editable HTML |
| `error.provider.*` | Invalid keys, safety blocks, quota/access/rate limits, unavailable models and generic provider failures |
| `error.export.*` | Runtime/converter/output/schema/path/permission/timeout and PPTX export failures |

Specific generation codes consumed by the frontend include
`error.template_not_found`, `error.template_layout_not_object`,
`error.bundled_template_unavailable`, `error.template_layout_invalid_json`,
`error.template_layout_min_one`, `error.template_id_required`,
`error.template_layout_not_found`, `error.presentation_not_found`,
`error.slides_must_be_positive`, `error.slides_too_many`,
`error.slides_toc_min`, `error.community_refs_smart_only`,
`error.prompt_required`, `error.outlines_required`,
`error.outlines_too_many`, `error.layout_min_one`,
`error.not_prepared_for_stream`, `error.outlines_empty`,
`error.presentation_data_invalid`, `error.presentation_layout_empty`,
`error.presentation_structure_mismatch`,
`error.presentation_layout_invalid`, `error.uuid_required`,
`error.slide_not_found`, `error.slide_mismatch`, `error.content_required`,
`error.generation_failed`, and `error.generation_task_not_found`.

Export codes are emitted for forward compatibility but currently map to a
generic localized frontend error rather than one catalog entry per code.
Unclassified provider responses remain plain legacy HTTP errors.

### 10.5 Frontend resolution rules

- `i18n/backend-messages.ts` owns typed status/error mappings.
- A recognized code always wins over legacy prose; params are passed to the
  catalog as interpolation values.
- An absent or unknown code falls back to the sanitized legacy message.
- Legacy prose heuristics remain only for compatibility with older backends.
- State transitions must use event/code state and never translated text.
- `ApiResponseHandler` resolves coded API errors centrally, while preserving
  the code and params on `ApiError`.

## 11. Presentation-language compatibility contract

- `LanguageType` uses stable lowercase snake_case codes internally.
- `LANGUAGE_LABEL_KEY` maps every code to localized catalog copy.
- `LEGACY_LANGUAGE_VALUE` serializes each code back to the exact historical
  API value because backend OCR and prompt paths still consume those strings.
- `parseLanguageValue` accepts both stable codes and historical display values;
  unknown/empty input returns `null`.
- There are 90 frontend language choices. All 89 backend OCR keys match their
  legacy values byte-for-byte; Auto is the sole frontend-only value.
- New sessions default to Vietnamese. Auto remains selectable, and saved
  selections override defaults.

## 12. Known compatibility notes

- The legacy `"image exceeds 5 MB maximum"` comparison has no producer in the
  current web or API repository. It remains only as an external/legacy fallback.
- Async task diagnostic `message` fields are not browser UI and remain uncoded;
  template polling already uses stable task status values.
- Removing legacy English payload fields, prose fallbacks, or the legacy
  presentation-language serializer requires a separate compatibility review.
